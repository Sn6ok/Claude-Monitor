# Windows Bridge

> Bridge — це спостерігач. Він читає файли, які Claude Code веде у будь-якому
> разі, і надсилає з них короткі структуровані події. Він не запускає Claude,
> не втручається в його роботу і не може її сповільнити.

---

## 1. Життєвий цикл

Master Prompt (Частина 5 §3, §4) ставить вимогу, яка на перший погляд
суперечлива: Bridge має стартувати разом із Claude Desktop, але **не разом
із Windows**.

Розвʼязання — офіційний механізм хуків Claude Code.

```text
Windows завантажилася
        │
        ▼
   нічого не запущено                        ← вимога виконана
        │
        │  користувач відкриває Claude Desktop
        │  і починає сесію Claude Code
        ▼
   хук SessionStart
        │
        ├── Bridge уже працює?  →  передати подію в канал і вийти
        │
        └── ні  →  запустити фоновий Bridge
                        │
                        ▼
              OpenProcess(Claude Desktop)
              WaitForSingleObject(…)          ← 0% CPU в очікуванні
                        │
                        │  користувач закриває Claude Desktop
                        ▼
              дескриптор сигналізовано
                        │
                        ▼
              коректне завершення (таймаут 3 с)
```

Ключова деталь: очікування завершення Claude Desktop реалізоване через
**дескриптор процесу як обʼєкт синхронізації**. Потік блокується в ядрі
й прокидається рівно в момент завершення. Циклу «перевір і поспи» немає.

### Коли вікно Claude Desktop закрили

Сесії Claude Code переживають закриття вікна: процес CLI працює далі, і Claude
продовжує відповідати. Тому сигнал від дескриптора більше не означає негайну
зупинку:

1. Bridge перевіряє, чи Claude Desktop не запустили знову, — і просто
   прив'язується до нового процесу;
2. якщо ні, але задачі під наглядом лишилися, Bridge працює далі й шукає
   Claude Desktop раз на 30 секунд;
3. зупиняється він, лише коли немає ні Claude Desktop, ні задач — через
   п'ять хвилин після зникнення вікна.

Раніше Bridge ішов слідом за вікном. На телефоні від цього лишався застиглий
чат: Claude відповідав далі, а застосунок показував останній стан
і позначку «дані застаріли».

### Захист від дублікатів

Іменований мʼютекс `Local\ClaudeMonitorBridge.v1`. Простір `Local\`
обмежує його сеансом користувача: у кожного користувача Windows свій
Claude Desktop і свій Bridge.

Мʼютекс звільняється операційною системою при закритті дескриптора —
зокрема й після аварійного завершення. Тому «зависла» блокування
неможлива.

## 2. Визначення кореневого процесу Claude Desktop

Усі процеси застосунку називаються `claude.exe`, тож імʼя нічого не
вирішує (докладніше — [research.md §1](research.md)).

```text
Claude.exe (кореневий)            ← його батько не належить до групи
├── Claude.exe --type=gpu-process
├── Claude.exe --type=renderer
├── Claude.exe --type=utility …
└── claude.exe (claude-code\…)    ← окремий бінарник, це Claude Code
```

Кореневим вважається процес, який:

1. має шлях до встановленого Claude Desktop (`\WindowsApps\Claude` або
   `\AnthropicClaude\`);
2. **не** лежить у каталозі `\claude-code\`;
3. чий батьківський процес не входить до тієї самої групи.

Якщо коренів кілька (буває після оновлення застосунку), береться найстаріший:
саме він тримає сесію.

**Чого тут навмисно немає.** Ранній варіант читав командні рядки чужих
процесів через PEB, щоб знайти аргумент `--type=`. Це вимагало доступу до
памʼяті іншого процесу, чого Частина 5 §11 Master Prompt велить уникати.
Дерево процесів дає ту саму відповідь без такого доступу, тому читання
памʼяті прибрано повністю.

## 3. Два потоки

```text
   ПОТІК СПОСТЕРЕЖЕННЯ                    ПОТІК МЕРЕЖІ
   ───────────────────                    ────────────
   WaitForMultipleObjects(                connect → auth
     каталог сесій,                            │
     каталог транскриптів,                     ▼
     дескриптор Claude Desktop,          блокуюче читання
     подія завершення)                   надсилання з черги
        │                                перепідключення
        ▼                                      ▲
   читання нових рядків                        │
        │                                      │
        ▼                                      │
   нормалізація                                │
        │                                      │
        ▼                                      │
   ЧЕРГА ───────────────────────────────────────┘
   (обмежена, потокобезпечна)
```

Розділення — вимога архітектури, а не оптимізація. Потік спостереження
кладе подію в чергу й одразу повертається до читання. Затримка мережі,
обрив звʼязку чи зависання Relay **фізично не можуть** дійти до читача
транскриптів, а отже — вплинути на Claude Code.

> Це рішення прийнято не одразу. Перший варіант робив усе в одному потоці
> з «неблокуючим» читанням. Виявилося, що `WINHTTP_OPTION_RECEIVE_TIMEOUT`
> не діє на дескриптор WebSocket: читання блокувалося назавжди, і головний
> цикл зупинявся. Наскрізна перевірка це виявила, після чого мережу
> винесено в окремий потік.

## 4. Джерела даних

Три джерела, усі перевірені емпірично ([research.md §3](research.md)).

### Реєстр сесій

`~/.claude/sessions/<pid>.json` — Claude Code створює такий файл на кожну
сесію. Дає перелік активних задач: ідентифікатор, PID, робочий каталог,
час старту, автоматичну назву.

Мертві записи відкидаються: перевіряється не лише існування PID, а й час
створення процесу. Номери процесів переви́користовуються, і без цієї
перевірки файл від давно померлої сесії міг би «оживити» чужий процес.

### Транскрипти

`~/.claude/projects/<slug>/<sessionId>.jsonl` — append-only файл, який
Claude Code веде незалежно від Bridge.

Читання інкрементальне, з останнього зміщення. Файл відкривається з повним
набором прапорців спільного доступу, тож Bridge не заважає Claude Code
писати в нього навіть тимчасово.

Якщо файл раптом став меншим — його підмінили або сесію перезапустили;
зміщення скидається, щоб не розбирати сміття.

### Хуки

Використовуються рівно три, і всі рідкісні:

| Хук | Навіщо |
|---|---|
| `SessionStart` | запустити Bridge |
| `SessionEnd` | коректно завершити задачу |
| `Notification` | єдиний надійний спосіб дізнатися, що Claude чекає на дозвіл |

`PreToolUse` і `PostToolUse` **не використовуються навмисно**: вони
спрацьовують на кожен виклик інструмента, а `PreToolUse` ще й блокує
Claude Code до свого завершення. Ті самі дані вже є в транскрипті.

Хук-процес нічого не робить сам: він передає дані в іменований канал
і одразу завершується. Заміряний час — **18 мс**.

## 5. Нормалізація подій

```text
рядок транскрипту                        подія протоколу
─────────────────────────────────────    ──────────────────────────────
assistant / tool_use  name=Edit          activity  edit_file  a.cpp
                      input.file_path

assistant / tool_use  name=Bash          activity  run_command  npm test
                      input.command

assistant / text                         output  «текст частинами по 3072 байти»

assistant / stop_reason=end_turn         status  idle

user / toolUseResult.stderr ≠ ""         result  error  «текст»

hook Notification                        status  waiting  «текст запиту»

user / content[] type=image              prompt  img=N  (самих зображень немає)

queue-operation  <task-notification>     нічого: службовий запис Claude Code
```

Перед постановкою в чергу кожна подія проходить:

1. **розбиття** на частини по 3072 байти (обрізання — лише понад 256 КБ);
2. **маскування секретів** (див. [security.md §5](security.md));
3. **дедуплікацію** — той самий стан поспіль не надсилається;
4. **пріоритезацію** — HIGH / MEDIUM / LOW;
5. **нумерацію** — монотонний лічильник на весь Bridge.

**Що не передається ніколи:** вміст файлів і аргументи інструментів крім
шляху чи команди. Зображення із запиту — теж: передається лише їхня
кількість, щоб запит «подивись на фото» не виглядав порожнім.

Службові записи, які Claude Code кладе у чергу від свого імені
(`<task-notification>` про завершення фонової команди й подібні), у стрічку
не потрапляють: вони виглядали як повідомлення користувача, хоча він їх
не писав.

Запити користувача, репліки Claude і вивід команд передаються повністю
(частинами, з маскуванням секретів). Блок `thinking` із текстом теж
вважається реплікою: Claude Desktop показує його в чаті, і частина
повідомлень Claude записується в транскрипт саме так. Порожній `thinking`
(лише підпис) нічого не несе й не передається.

## 6. Стани задач

Кожен стан має спостережуваний доказ. Стану «здогадка» не існує.

| Стан | Доказ |
|---|---|
| `starting` | сесія в реєстрі, транскрипт ще порожній |
| `working` | є `tool_use`, на який ще немає `tool_result` |
| `waiting` | прийшов хук `Notification` (Claude просить дозволу чи відповіді) |
| `idle` | `stop_reason: end_turn` |
| `error` | `stderr` непорожній або `is_error: true` |
| `limited` | репліка з `error: rate_limit` — вичерпано ліміт використання; коли настає час скидання, задача сама повертається в `idle` |
| `finished` | сесія коректно завершилася |
| `gone` | сесія зникла з реєстру без завершення |
| `unknown` | транскрипт нечитабельний, формат змінився |

`unknown` — не помилка реалізації, а обовʼязковий чесний стан
(Частина 5 §12, Частина 6 §42 Master Prompt). Якщо Claude Code оновиться
й формат зміниться, монітор скаже «не знаю», а не вигадає стан.

Розрізнення `finished` і `gone` теж принципове: сесія, яка просто зникла,
не є «успішно завершеною».

## 7. Черга подій

```text
MAX_QUEUE_EVENTS   512 подій
MAX_QUEUE_BYTES    2 МБ
MAX_EVENT_TEXT     3072 байти
MAX_SESSIONS       16 задач
MAX_FINISHED       20 в історії
```

При переповненні витісняються найменш важливі події:

| Пріоритет | Події | Витісняється |
|---|---|---|
| HIGH | зміни стану, помилки, поява й зникнення задач | **ніколи** |
| MEDIUM | успішні результати, активність | після LOW |
| LOW | текстовий вивід, повторювана активність | першим |

Гарантія: користувач може не побачити частини проміжного виводу, але
завжди побачить, що задача завершилася або впала.

Перевірено тестом: 50 000 подій без мережі не вичерпують памʼять.

## 8. Режими запуску

```powershell
claude-monitor-bridge.exe                  # робочий режим
claude-monitor-bridge.exe --pair           # підключити телефон (до 5 телефонів)
claude-monitor-bridge.exe --unpair ID      # від'єднати телефон за початком ідентифікатора
claude-monitor-bridge.exe --unpair         # від'єднати всі телефони
claude-monitor-bridge.exe --status         # діагностика й перелік телефонів
claude-monitor-bridge.exe --set-relay URL  # адреса сервера
claude-monitor-bridge.exe --install-hooks  # показати налаштування хуків
claude-monitor-bridge.exe --hook ПОДІЯ     # службовий виклик
```

Додаткові прапорці: `--log-level`, `--console`, `--allow-insecure`.

До одного ноутбука можна підключити до п'яти телефонів. Кожен має власний
ключ шифрування й отримує власні кадри: те, що зашифровано для одного
телефона, інший не прочитає. Шостий телефон `--pair` не підключить — він
покаже перелік і підкаже, котрий від'єднати. Робочий Bridge помічає зміни
переліку сам (раз на 5 с), перезапускати його не треба.

Лічильник nonce кожного з'єднання стартує з позначки часу, а не з нуля:
ключ між з'єднаннями сталий, і старт із нуля означав би повтор nonce після
кожного перепідключення.

## 9. Зберігання даних

```text
%USERPROFILE%\.claude-monitor\
├── bridge.json      конфігурація: адреса Relay, рівень журналу
├── identity.bin     приватні ключі під DPAPI
├── peer.json        публічні ключі спарених телефонів (до 5)
└── bridge.log       журнал, ротація на 1 МБ
```

Приватні ключі зашифровані DPAPI з прапорцем `CRYPTPROTECT_UI_FORBIDDEN`:
розшифрувати їх може лише той самий обліковий запис Windows на цій самій
машині, і жодне модальне вікно не зʼявиться у фоновому процесі.

Журнал не скидається на диск після кожного запису: постійний дисковий
ввід-вивід заборонений Частиною 5 §34 Master Prompt.

## 10. Технічні рішення та їх причини

| Рішення | Причина |
|---|---|
| C++20, лише Win32 API | немає runtime, немає GC; бінарник 388 КБ, RAM 13 МБ |
| WinHTTP замість бібліотеки | входить у Windows; системна перевірка сертифікатів і підтримка проксі |
| CNG + DPAPI | системна криптографія без зовнішніх залежностей |
| Власний парсер JSON | ~400 рядків замість бібліотеки на сотні кілобайтів |
| Статичне лінкування CRT | не потрібен Visual C++ Redistributable |
| `ReadDirectoryChangesW` | подієва модель замість опитування: 0% CPU у спокої |
| Дескриптор процесу для очікування | те саме, для життєвого циклу |
