### Пояснення кожної стрілки

Частина 2 §19 Master Prompt вимагає пояснити кожну стрілку.

| # | Стрілка | Механізм | Напрямок | Хто ініціює | Вплив на Claude Code |
|---|---|---|---|---|---|
| 1 | Claude Code -> транскрипт | append у JSONL-файл, який Claude Code веде **у будь-якому разі** | одностороння | Claude Code | нульовий: Bridge лише читає |
| 2 | Claude Code -> реєстр сесій | JSON-файл на сесію, ведеться **у будь-якому разі** | одностороння | Claude Code | нульовий |
| 3 | Claude Code -> hook | запуск `bridge.exe --hook` із JSON на stdin | одностороння | Claude Code | лише 3 рідкісні події; hook завершується за мілісекунди |
| 4 | Bridge -> Relay | WebSocket over TLS, вихідне зʼєднання | двостороння | **Bridge** | асинхронна, окремий потік; ніколи не блокує спостереження |
| 5 | Relay -> Android | WebSocket over TLS, вихідне зʼєднання | двостороння | **Android** | немає звʼязку з Claude Code взагалі |

Стрілки 4 і 5 — **обидві вихідні**. Ані на ноутбуці, ані на телефоні не відкривається
жодного вхідного порту (Частина 5 §26). Це знімає проблеми NAT і фаєрволу.

## 2. Розподіл відповідальності

Головне правило (Частина 2 §20):

> **Claude Code виконує роботу. Bridge тільки спостерігає. Relay тільки маршрутизує.
> Android тільки відображає.**

| Компонент | Робить | Категорично не робить |
|---|---|---|
| **Claude Code** | усю корисну роботу | нічого не знає про існування монітора |
| **Bridge** | читає файли, нормалізує події, шифрує, відправляє | не запускає Claude, не робить screen capture, не виконує AI-задач, не керує Claude |
| **Relay** | автентифікація, авторизація, маршрутизація, ліміти | не дешифрує корисне навантаження, не має доступу до файлів ноутбука, не зберігає історію |
| **Android** | показує стан | не виконує команд, не керує ноутбуком, не транслює екран |

## 3. Windows Bridge — внутрішня будова

```text
                     bridge.exe (один процес, два робочі потоки)
   ┌───────────────────────────────────────────────────────────────┐
   │                                                               │
   │  ПОТІК СПОСТЕРЕЖЕННЯ                                          │
   │     WaitForMultipleObjects(                                   │
   │        каталог ~/.claude/sessions,   <- ReadDirectoryChangesW  │
   │        каталог ~/.claude/projects,   <- ReadDirectoryChangesW  │
   │        дескриптор Claude Desktop,    <- його завершення        │
   │        подія завершення,                                      │
   │        канал хуків )                 <- named pipe             │
   │     0% CPU у стані очікування                                 │
   │                          │                                    │
   │                          ▼                                    │
   │              ┌────────────────────┐                           │
   │              │  NORMALIZER        │  JSONL -> події протоколу  │
   │              │  + REDACTOR        │  маскування секретів       │
   │              │  + STATE MACHINE   │  IDLE/WORKING/WAITING/...  │
   │              └─────────┬──────────┘                           │
   │                        ▼                                      │
   │              ┌────────────────────┐                           │
   │              │  BOUNDED QUEUE     │  ліміт 512 подій, 2 МБ     │
   │              │  + SNAPSHOT        │  витіснення LOW-пріоритету │
   │              └─────────┬──────────┘                           │
   │                        │ (неблокуюча передача)                │
   │  ПОТІК МЕРЕЖІ          ▼                                      │
   │     WinHTTP WebSocket over TLS -> Relay                       │
   │     блокуюче читання, exponential backoff при обриві          │
   │     затримки мережі НЕ доходять до спостереження              │
   └───────────────────────────────────────────────────────────────┘
```

### Чому два потоки, а не один

Початковий задум був простішим: один потік, який після кожної події
дочитує мережу «неблокуюче». Він не запрацював.

`WinHttpSetOption(WINHTTP_OPTION_RECEIVE_TIMEOUT)` **не діє на дескриптор
WebSocket**: читання блокувалося назавжди, і головний цикл зупинявся,
так і не дійшовши до відправлення. Неблокуючого читання WebSocket
у WinHTTP немає взагалі.

Це виявила наскрізна перевірка, після чого мережу винесено в окремий
потік — як і вимагає Частина 5 §19 Master Prompt.

### Що це дає

* **Спостереження не залежить від мережі.** Потік читання кладе подію
  в чергу й одразу повертається. Обрив звʼязку, зависання Relay чи повільна
  мережа фізично не можуть його затримати — а отже, не можуть вплинути
  на Claude Code.
* **Жодного циклу опитування.** Обидва потоки блокуються на обʼєктах ядра.
  У стані спокою процес споживає 0% CPU (Частина 5 §31–32) — заміряно.
* **Життєвий цикл і канал хуків не потребують власних потоків.** Дескриптор
  процесу Claude Desktop і named pipe очікуються тим самим
  `WaitForMultipleObjects`, що й зміни у файлах.
* **Hook-процес не чекає на мережу.** Він записує подію в канал і одразу
  завершується — заміряні 18 мс (Частина 5 §2).

### Життєвий цикл

```text
Windows завантажилась
        │
        ▼
   нічого не запущено                              <- Частина 5 §3 виконана
        │
        │  користувач відкриває Claude Desktop
        │  і починає сесію Claude Code
        ▼
   SessionStart hook -> bridge.exe --hook session-start
        │
        ├─ named mutex "Global\ClaudeMonitorBridge"
        │     вже існує? -> передати подію в pipe і вийти   <- Частина 5 §8
        │     не існує?  -> запустити фоновий Bridge
        ▼
   BRIDGE РОБОЧИЙ
        │  OpenProcess(root Claude Desktop) -> hClaudeDesktop
        │  WaitForSingleObject(hClaudeDesktop)     <- 0% CPU
        │
        │  користувач закриває Claude Desktop
        ▼
   handle сигналізовано
        │
        ▼
   graceful shutdown (таймаут 2 с на мережу)       <- Частина 5 §36
        │
        ▼
   процес завершено
```

Наступний запуск Claude Desktop -> новий `SessionStart` -> новий Bridge.
Дублікати неможливі завдяки named mutex.

## 4. Машина станів Bridge

```text
        ┌─────────────┐
        │  STARTING   │  ініціалізація, читання конфігурації
        └──────┬──────┘
               ▼
        ┌─────────────┐
        │  DETECTING  │  пошук root-процесу Claude Desktop
        └──────┬──────┘
               │ знайдено
               ▼
        ┌─────────────┐      немає ключів
        │ INTEGRATION ├──────────────────> ┌──────────────┐
        │    READY    │                    │  UNPAIRED    │
        └──────┬──────┘                    │ (чекає pair) │
               │                           └──────┬───────┘
               ▼                                  │ спарено
        ┌─────────────┐ <────────────────────────┘
        │ CONNECTING  │  TLS + автентифікація на Relay
        └──────┬──────┘
               │ автентифіковано
               ▼
        ┌─────────────┐  обрив звʼязку   ┌───────────────┐
        │ MONITORING  ├─────────────────>│ RECONNECTING  │
        │             │<─────────────────┤ (backoff)     │
        └──────┬──────┘   відновлено     └───────────────┘
               │ Claude Desktop завершився
               ▼
        ┌─────────────┐
        │ SHUTTING    │  фінальний статус, закриття сокета
        │    DOWN     │
        └──────┬──────┘
               ▼
        ┌─────────────┐
        │   STOPPED   │
        └─────────────┘
```

**Важливо:** у станах `UNPAIRED`, `CONNECTING`, `RECONNECTING` потік OBSERVER
продовжує працювати і наповнювати чергу. Claude Code не помічає жодної різниці.

## 5. Стани Claude Code, які показує монітор

Bridge виводить стан із транскрипту за чіткими правилами. Кожен стан має
доказ — не здогадку (Частина 5 §10, §12).

| Стан | Доказ у даних | Що бачить користувач |
|---|---|---|
| `NOT_RUNNING` | немає жодного файлу `sessions/<pid>.json` із живим PID | Claude Code не запущено |
| `STARTING` | сесія зареєстрована, але транскрипт ще порожній | Запускається |
| `WORKING` | останній запис — `assistant` із `tool_use`, на який ще немає `tool_result` | Працює |
| `WORKING` | останній запис — `assistant` із `stop_reason: tool_use` | Працює |
| `WAITING` | отримано hook `Notification` (запит дозволу) і після нього немає нових записів | Чекає на вашу відповідь |
| `IDLE` | останній запис — `assistant` із текстом і `stop_reason: end_turn` | Завершив, очікує |
| `ERROR` | `toolUseResult.stderr` непорожній або `is_error: true` у `tool_result` | Помилка |
| `UNKNOWN` | транскрипт нечитабельний / формат змінився після оновлення | Невідомо |

`UNKNOWN` — не помилка реалізації, а **обовʼязковий чесний стан** за Частиною 5 §44
і Частиною 6 §42. Якщо Claude Code оновиться і формат транскрипту зміниться,
монітор покаже `UNKNOWN`, а не вигадає стан.

## 5.1 Модель мультизадачності

Розвідка показала, що на машині **одночасно працюють кілька сесій Claude Code**
(на момент дослідження — три). Тому монітор від початку будується як
багатозадачний, а не як «один екран одного статусу».

### Один Bridge на машину, не на сесію

```text
                 ┌──────────────────────────────┐
                 │      ОДИН bridge.exe          │
                 │                               │
   ~/.claude/    │   SessionRegistry             │
   sessions/ ───>│   ├── sid=fa676105 (проєкт A) │──┐
     *.json      │   ├── sid=9c02aa71 (проєкт B) │  │ усі події
                 │   └── sid=17d4be03 (проєкт C) │  │ мають sid
                 │                               │  │
   транскрипти ─>│   по одному спостерігачу      │  ▼
   */*.jsonl     │   на активну сесію            │ Relay -> Android
                 └──────────────────────────────┘
```

Перший `SessionStart` hook запускає Bridge. Наступні сесії Bridge виявляє
**сам**, через `ReadDirectoryChangesW` на каталозі `~/.claude/sessions/` —
додаткові hook-виклики для цього не потрібні.

### Дані картки задачі — усе з реальних джерел

| Поле UI | Джерело | Що якщо джерела немає |
|---|---|---|
| ідентифікатор | `sessionId` з реєстру | задача не показується взагалі |
| назва | `custom-title.customTitle` | -> `sessions.name` -> `last-prompt` -> назва каталогу |
| проєкт | остання частина `cwd` | `—` |
| гілка | `gitBranch` із транскрипту | не показується |
| стан | машина станів по транскрипту | `UNKNOWN` |
| поточна дія | останній `tool_use` | `—` |
| час роботи | `startedAt` із реєстру | не показується |
| останнє оновлення | час останньої події | позначка `STALE` |

Поле `title_src` у протоколі несе **джерело назви**, тому UI може чесно
показати, що назва похідна від промпту, а не задана людиною.

### Правила ізоляції задач

Ці правила є технічними гарантіями, а не побажаннями:

1. **Кожна подія обов'язково несе `sid`.** Подія без `sid` або з невідомим
   `sid` відкидається приймачем. Приписати її «поточній» задачі неможливо —
   поняття «поточної задачі» в моделі даних просто немає.
2. **Стан зберігається у `Map<sid, SessionState>`.** Немає жодного глобального
   поля стану, яке дві задачі могли б перезаписати одна одній.
3. **Помилка ізольована.** `ERROR` виставляється конкретному `sid`;
   решта задач не змінюють свого стану.
4. **Зникнення задачі явне.** Якщо сесія зникла з реєстру, вона переходить
   у `finished`/`gone` і **не передає** свої дані іншій задачі.
5. **Час роботи рахується окремо** для кожної задачі, від власного `startedAt`.

### Обмеження пам'яті

| Обмеження | Значення | Причина |
|---|---|---|
| активних задач одночасно | 16 | понад це — найстаріші перестають відстежуватись |
| завершених задач в історії | 20 | кільцевий буфер, витісняє найстаріші |
| подій на задачу в пам'яті Android | 2000 | і до 1,5 млн символів; знімок лише доповнює, не замінює |
| подій у глобальній стрічці | 2000 | і до 1,5 млн символів; витісняється найдавніше |

Жодна структура не росте необмежено (Частина 4 §21, Частина 5 §16, §33).

### Чесне обмеження

Якщо майбутня версія Claude Code перестане вести `~/.claude/sessions/*.json`,
Bridge зможе відстежувати лише ту сесію, яка повідомила про себе через hook.
У такому разі UI покаже рівно ті задачі, які **надійно виявлені** — і не
вигадає решти. Модель даних і UI залишаються багатозадачними в будь-якому разі.

Screen scraping, читання пам'яті чи інжект заради виявлення додаткових задач
**не застосовуються** за жодних обставин.

## 6. Нормалізація подій

```text
Рядок JSONL                                Подія протоколу
─────────────────────────────────────────  ──────────────────────────────────
assistant / content[].type=tool_use        {type:"activity", action:"edit_file",
  name="Edit", input.file_path="a.cpp"      target:"a.cpp"}

assistant / content[].type=tool_use        {type:"activity", action:"run_command",
  name="Bash", input.command="npm test"     target:"npm test"}

assistant / content[].type=text            {type:"output", text:"<до 3 КБ, довше — частинами>"}

user / toolUseResult.stderr != ""          {type:"result", status:"error",
                                            text:"<до 3 КБ, довше — частинами>"}

user / toolUseResult.stdout                {type:"result", status:"success",
                                            text:"<до 3 КБ, довше — частинами>"}

assistant / stop_reason="end_turn"         {type:"status", state:"idle"}

hook Notification                          {type:"status", state:"waiting",
                                            text:"<текст запиту>"}
```

Правила, які застосовуються до кожної події перед постановкою в чергу:

1. **Розбиття** — текст понад `MAX_EVENT_TEXT` (3072 байти) ділиться на частини; понад `MAX_OUTPUT_BYTES` (256 КБ) обрізається з позначкою.
2. **Маскування секретів** — консервативний набір патернів (див. [security.md](security.md)).
3. **Дедуплікація** — однаковий стан поспіль не відправляється (Частина 2 §6).
4. **Пріоритезація** — HIGH / MEDIUM / LOW для витіснення з переповненої черги.
5. **Нумерація** — монотонний `sequence`, який ніколи не повторюється в межах сесії.

**Не передається ніколи:** вміст файлів проєкту й аргументи інструментів крім
шляху/команди. Запити, репліки Claude (зокрема `thinking`-блоки з текстом, які
Claude Desktop показує в чаті) і вивід команд ідуть повністю, з маскуванням секретів.

## 7. Snapshot проти потоку подій

Дві моделі даних (Частина 2 §14):

* **Snapshot** — повний поточний стан. Малий, повністю самодостатній.
  Надсилається при підключенні телефона, при reconnect і при виявленні розриву
  в нумерації.
* **Event** — одна зміна. Надсилається лише коли щось справді змінилося.

```text
Телефон підключається
        │
        ▼  AUTH
   автентифіковано
        │
        ▼  SNAPSHOT_REQUEST
   Bridge надсилає SNAPSHOT (стан + останні N подій)
        │
        ▼
   UI повністю відновлено
        │
        ▼  далі лише EVENT-и
```

Це прибирає потребу зберігати довгу історію будь-де (Частина 4 §6).

## 8. Модель довіри Relay

Частина 3 §14 вимагає явно задокументувати, що знає кожен учасник.

| Учасник | Знає | Не знає |
|---|---|---|
| **Bridge** | усе про локальну сесію | приватний ключ телефона |
| **Relay** | ідентифікатори пристроїв, публічні ключі, розміри й час повідомлень, `session_id` | **вміст подій** — він зашифрований наскрізно |
| **Android** | усе, що надіслав Bridge | приватний ключ ноутбука |
| **Стороння особа** | нічого, навіть знаючи адресу Relay | усе |

Обрано **наскрізне шифрування (E2EE)** поверх TLS. Обґрунтування:

* Relay за замовчуванням крутиться через Cloudflare Tunnel — тобто трафік проходить
  через інфраструктуру третьої сторони. TLS там термінується.
* Події Claude Code містять шляхи до файлів і фрагменти коду користувача.
* Частина 3 §15 вимагає мінімізувати те, що бачить Relay.

Отже Relay бачить лише конверт маршрутизації, а не вміст. Це чесно відображається
в UI застосунку як `E2E encrypted` — і це твердження є правдивим (Частина 6 §42).

## 9. Технологічний стек і обґрунтування

| Компонент | Вибір | Чому саме він |
|---|---|---|
| Bridge | **C++20, MSVC, лише Win32 API** | Master Prompt Ч.6 §6 ставить C++ пріоритетом. Немає runtime, немає GC, бінарник ~300 KB, RAM ~4 МБ. Тулчейн уже є й перевірений. |
| Bridge: TLS+WebSocket | **WinHTTP** (`WinHttpWebSocketCompleteUpgrade`) | вбудовано у Windows: нуль зовнішніх залежностей, валідація сертифікатів системна, автоматично використовує системний проксі |
| Bridge: криптографія | **CNG (BCrypt/NCrypt) + DPAPI** | системні бібліотеки, без власної криптографії (Ч.3 §25); ключ під захистом облікового запису |
| Bridge: JSON | власний потоковий парсер (~400 рядків) | єдина альтернатива — тягнути бібліотеку заради розбору JSONL; Ч.4 §30 і Ч.6 §39 забороняють зайві залежності |
| Relay | **Node.js + `ws`** | Node уже встановлено; `ws` не має транзитивних залежностей; TLS вбудований |
| Android | **Kotlin + Jetpack Compose (мінімально)** | Ч.6 §5 віддає перевагу нативному Android; Compose допустимий |
| Android: WebSocket | **OkHttp** | де-факто стандарт, коректна робота зі зміною мережі |
| Android: ключі | **Android Keystore + EncryptedSharedPreferences** | вимога Ч.3 §5 |
| Транспорт | **WebSocket over TLS (WSS)** | див. порівняння нижче |

### Чому WebSocket, а не HTTP/2 чи QUIC

Частина 2 §7 вимагає порівняти варіанти, а не брати WebSocket автоматично.

| Критерій | WSS | HTTP/2 SSE | HTTP/3 / QUIC |
|---|---|---|---|
| Двонаправленість | так, нативно | ні (лише сервер->клієнт) | так |
| Підтримка у Win32 без залежностей | **так, WinHTTP** | частково | **ні** — потрібна зовнішня бібліотека |
| Підтримка на Android без залежностей | так (OkHttp) | так | потребує новішого OkHttp |
| Проходження через корпоративні проксі | **найкраще** | добре | часто блокується UDP |
| Накладні витрати на кадр | 2–6 байт | ~9 байт HTTP/2 frame | ~20+ байт |
| Складність реалізації | низька | середня | висока |
| Готовність до `Phone -> Laptop` у майбутньому | **так** | ні | так |

**Рішення: WSS.** HTTP/3 вимагав би тягнути msquic або аналог у Bridge — це прямо
суперечить вимозі мінімального dependency footprint. SSE не дає зворотного каналу,
який знадобиться для майбутніх `STOP`/`PAUSE` (Частина 2 §11).

## 10. Що відбувається при відмовах

| Відмова | Поведінка системи | Claude Code |
|---|---|---|
| Немає інтернету на ноутбуці | черга наповнюється до 512 подій, далі витісняє LOW | **працює нормально** |
| Relay недоступний | backoff 1-2-4-8-16-30-60 с із джитером | **працює нормально** |
| Bridge аварійно завершився | процес зникає; наступний hook підніме новий | **працює нормально** |
| Телефон втратив мережу | Android перепідключається, отримує свіжий snapshot | **працює нормально** |
| Wi-Fi -> мобільний інтернет | OkHttp виявляє зміну, перепідключення | **працює нормально** |
| Relay перезапустився | обидві сторони перепідключаються | **працює нормально** |
| Некоректний пакет | відхиляється валідатором, зʼєднання розривається | **працює нормально** |
| Claude Desktop оновився | якщо формат транскрипту змінився -> стан `UNKNOWN` | **працює нормально** |

Останній стовпець однаковий у кожному рядку — і це головний критерій успіху
архітектури (Частина 5 §2, Частина 6 §29).

## 11. Межі проєкту — чого система не робить

Це не обмеження реалізації, а свідомі архітектурні рішення (Частина 6 §55).

```text
НЕ реалізовано:  remote desktop, трансляція екрана, скріншоти,
                 перехоплення клавіатури й миші, виконання команд із телефона,
                 другий екземпляр Claude Code, AI всередині Bridge або Relay,
                 власна криптографія, обхід перевірки TLS,
                 необмежені черги, aggressive polling, busy loop,
                 запуск Bridge разом із Windows
```

Протокол **спроєктований так**, щоб напрямок `Phone -> Laptop` (`STOP`, `PAUSE`,
`REQUEST_STATUS`) можна було додати без перебудови системи, але в цій версії
Android залишається строго read-only (Частина 4 §27).
