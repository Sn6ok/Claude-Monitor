# Продуктивність

> Master Prompt (Частина 5 §28) прямо забороняє робити висновок «легкий»
> без вимірювань. Усі цифри нижче — результати запуску `scripts/benchmark.ps1`
> та `scripts/longrun.ps1` на реальній системі, а не оцінки.

---

## 1. Заміряні цифри

Машина: Windows 11 Pro 10.0.26200, вимірювання під час роботи трьох
одночасних сесій Claude Code.

| Режим | RAM середня | RAM пік | CPU | Потоків | Диск |
|---|---|---|---|---|---|
| Bridge, мережа недоступна | 13.0 МБ | 13.2 МБ | 0.004% | 10 | 3.4 КБ |
| Bridge, підключений | 13.1 МБ | 13.2 МБ | 0.000% | 9 | 1.7 КБ |
| Bridge + приєднаний монітор | 13.1 МБ | 13.2 МБ | 0.000% | 8 | 3.3 КБ |
| Relay | 49.4 МБ | 49.4 МБ | 0.000% | 13 | 0 КБ |

| Артефакт | Розмір |
|---|---|
| `claude-monitor-bridge.exe` | 388 КБ |
| `app-release.apk` | 1.32 МБ |

Свіжі результати щоразу перезаписуються у
[benchmark-results.md](benchmark-results.md).

## 2. Як читати ці цифри

**RAB однакова в усіх трьох режимах.** Це і є головний результат: коли
мережа недоступна, черга подій наповнюється, але споживання не зростає.
Саме тут виявився б витік, якби він був.

**CPU 0.000%** означає, що процес більшість часу спить на обʼєктах ядра.
Це не округлення до нуля через малу вибірку: за 45 секунд Bridge витратив
менш ніж 0.01 секунди процесорного часу.

**Кількість потоків не росте.** 8–10 залежно від того, скільки внутрішніх
потоків Windows тримає для асинхронного вводу-виводу.

**Диск майже не використовується.** Кілька кілобайтів за хвилину — це
записи в журнал. Bridge не скидає буфери після кожного запису: постійний
дисковий ввід-вивід заборонений Частиною 5 §34 Master Prompt.

## 3. Чому саме такі результати

### Немає жодного циклу опитування

```text
що відбувається у стані спокою
──────────────────────────────
потік спостереження    WaitForMultipleObjects(…)   спить у ядрі
потік мережі           WinHttpWebSocketReceive     спить у ядрі
```

Обидва потоки блокуються на обʼєктах ядра і прокидаються **лише** коли:

- Claude Code дописав щось у транскрипт;
- зʼявилася або зникла сесія;
- прийшов кадр від Relay;
- спрацював запобіжний таймер (раз на 5 секунд).

Конструкції на кшталт `while (true) { перевірити(); Sleep(100); }`
у проєкті немає — Частина 5 §31–32 Master Prompt її прямо забороняє.

### Читання інкрементальне

Транскрипти сягають десятків мегабайтів. Bridge читає лише те, що
дописалося з моменту минулого читання, і за раз бере не більше мегабайта.
Пікова памʼять не залежить від розміру файлу.

### Немає runtime

C++ без винятків на гарячих шляхах, без RTTI, зі статичним лінкуванням CRT.
Немає збирача сміття, JIT-компілятора чи віртуальної машини — звідси
й 13 МБ проти сотень мегабайтів, які дав би Electron.

### Черга обмежена конструктивно

```text
512 подій, 2 МБ, 3072 байти на подію
```

При переповненні витісняються найменш важливі події. Зростати понад ці
межі черга не може за побудовою, а не за домовленістю.

## 4. Вплив на Claude Code

Найважливіше питання проєкту: чи не сповільнює монітор те, що спостерігає.

| Механізм | Вплив |
|---|---|
| Читання транскриптів | **нульовий** — Bridge лише читає файл, який Claude Code веде в будь-якому разі |
| Читання реєстру сесій | **нульовий** — те саме |
| Хук `SessionStart` | **18 мс** один раз за сесію |
| Хук `SessionEnd` | ~18 мс один раз за сесію |
| Хук `Notification` | ~18 мс на запит дозволу |
| Мережа | **нульовий** — окремий потік, зʼєднаний із рештою лише чергою |

Файли відкриваються з повним набором прапорців спільного доступу, тож
Bridge не блокує запис навіть на мить.

Хуки `PreToolUse` і `PostToolUse` **не використовуються навмисно**: вони
спрацьовували б на кожен виклик інструмента, а `PreToolUse` ще й затримує
Claude Code до свого завершення. Ті самі дані вже є в транскрипті.

### Що показав тест відмов

Найважливіший результат: після восьми сценаріїв, які навмисно ламали
моніторинг (аварійне завершення Bridge, падіння Relay, потік сміттєвих
пакетів), кількість процесів Claude Desktop і перелік активних сесій
лишилися незмінними — 13 процесів і 3 сесії до і після.

## 5. Мережевий трафік

| Що | Обсяг |
|---|---|
| Кадр `ping` | ~90 байтів, раз на 45 секунд |
| Подія `activity` | ~150–250 байтів |
| Пакет подій | до 8 подій в одному кадрі |
| Знімок стану | ~1–3 КБ залежно від кількості задач |
| Добовий фон без активності | ~200 КБ (самі лише ping) |

Стан не надсилається, якщо він не змінився: повторення того самого
статусу відсікається на рівні нормалізації (Частина 2 §6 Master Prompt).

Інтервал ping у 45 секунд обрано не випадково: типовий NAT-таймаут
мобільних операторів — 60–120 секунд, а Cloudflare розриває неактивний
WebSocket через 100 секунд.

## 6. Тривалий прогін

`scripts/longrun.ps1` періодично знімає RAM, кількість дескрипторів
і потоків. Пороги спрацювання:

| Показник | Поріг |
|---|---|
| Зростання RAM | +5 МБ |
| Зростання дескрипторів | +50 |
| Зростання потоків | +2 |

Вони підібрані так, щоб не реагувати на звичайні коливання розподільника
памʼяті, але помітити систематичне зростання. Результати останнього
прогону — [longrun-results.md](longrun-results.md).

## 7. Порівняння з альтернативами

Для розуміння, чого коштувала б інша архітектура:

| Підхід | RAM | CPU | Трафік |
|---|---|---|---|
| **Claude Monitor** | **13 МБ** | **~0%** | ~200 КБ/добу у спокої |
| Віддалений робочий стіл | 50–200 МБ | 5–20% | 1–10 МБ/хв |
| Electron-застосунок | 150–400 МБ | 1–5% | залежить |
| Опитування раз на секунду | 15–30 МБ | 0.5–2% | ~2 МБ/добу |

Різниця з останнім рядком показова: подієва модель дає не лише менший
CPU, а й менший трафік, бо повідомлення надсилаються тоді, коли є що
надсилати, а не за розкладом.

## 8. Як відтворити вимірювання

```powershell
# бенчмарк, три режими
.\scripts\benchmark.ps1 -SampleSeconds 60

# тривалий прогін
.\scripts\longrun.ps1 -Minutes 60

# тести відмов із перевіркою впливу на Claude Code
.\scripts\failure-tests.ps1
```

Скрипти самі піднімають власний Relay на окремому порту, тимчасово
переспрямовують на нього Bridge і наприкінці повертають вашу
конфігурацію.
