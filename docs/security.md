# Модель безпеки

> Головний принцип (Частина 3 §27 Master Prompt):
> **телефон бачить лише те, що дозволено саме йому; Relay не отримує зайвого;
> Bridge не чіпає секретів Claude; жоден секрет не лежить у застосунку
> чи у вихідному коді.**

---

## 1. Модель загроз

Система доступна через відкритий інтернет, тому припускається найгірше:
адреса сервера відома стороннім, трафік спостерігають, а клієнт може
бути підробленим.

### Від чого захищає повністю

| Загроза | Механізм захисту |
|---|---|
| Стороння особа знає адресу Relay | сама по собі адреса не дає нічого: потрібен зареєстрований ключ |
| Сканування портів сервера | єдиний відкритий маршрут — `/ws` і `/health`, обидва без даних |
| Підключення без авторизації | ECDSA-підпис одноразового виклику; невідомий пристрій відхиляється |
| Перехоплення трафіку | TLS, поверх нього — AES-256-GCM наскрізно |
| Повторне відтворення пакетів | одноразовий nonce + вікно часу ±5 хв + монотонні лічильники |
| Підбір коду підключення | 60 бітів ентропії, 3 хвилини життя, 5 спроб, далі 15 хв блокування |
| Знання чужого `session_id` | ідентифікатор нічого не дає: перевіряється звʼязок пристроїв |
| Підміна вмісту повідомлення | тег автентичності GCM; підроблене повідомлення відкидається цілком |
| Втрата телефона | відкликання діє негайно на активні зʼєднання |
| Сміттєві та завеликі пакети | валідація до розбору, жорсткі ліміти розміру |
| Вичерпання памʼяті сервера | обмежені черги, ліміт зʼєднань, витіснення неактивних записів |

### Від чого захищає частково

| Загроза | Що робиться | Що лишається |
|---|---|---|
| Секрети у виводі Claude Code | консервативне маскування | маскування вузьке навмисно (див. §5) |
| Оператор Relay | не бачить вмісту подій | бачить метадані: час, розміри, ідентифікатори |
| Компрометація Windows | ключі під DPAPI | зловмисник із правами користувача має доступ до всього так само |

### Що поза межами моделі

- Зловмисник із фізичним доступом до розблокованого ноутбука.
- Шкідливе програмне забезпечення з правами адміністратора на ноутбуці.
- Компрометація самого Claude Desktop.
- Цілеспрямований аналіз обсягу трафіку для висновків про активність.

Ці випадки не мають реалістичного захисту на рівні монітора: той, хто
контролює машину, і так бачить усе, що бачить Bridge.

## 2. Що знає кожен учасник

Частина 3 §14 Master Prompt вимагає задокументувати це явно.

| | Bridge | Relay | Android | Стороння особа |
|---|---|---|---|---|
| Вміст подій | так | **ні** | так | ні |
| Шляхи до файлів, команди | так | **ні** | так | ні |
| Назви задач | так | **ні** | так | ні |
| Ідентифікатори пристроїв | так | так | так | ні |
| Публічні ключі | так | так | так | ні |
| Час і розмір повідомлень | так | так | так | ні |
| Приватний ключ телефона | **ні** | **ні** | так | ні |
| Приватний ключ ноутбука | так | **ні** | **ні** | ні |
| Облікові дані Claude | **ні** | **ні** | **ні** | ні |

Останній рядок важливий: Bridge **не читає й не копіює** облікові дані
Claude. Він працює з транскриптами й реєстром сесій, де їх немає.

## 3. Криптографія

Жодного власного алгоритму. Усе — вбудовані засоби платформ
(Частина 3 §13, §25 Master Prompt).

| Призначення | Алгоритм | Windows | Android | Relay |
|---|---|---|---|---|
| Ідентичність | ECDSA P-256 + SHA-256 | CNG | Keystore | Node crypto |
| Формат підпису | IEEE P1363 (сирі r‖s) | нативно | `…inP1363Format` | `ieee-p1363` |
| Узгодження ключа | ECDH P-256 | CNG | Keystore | — |
| Похідні ключі | HKDF-SHA256 | CNG | `javax.crypto` | `hkdfSync` |
| Шифрування | AES-256-GCM | CNG | `AES/GCM/NoPadding` | — |
| Зберігання ключів | DPAPI | — | Keystore | — |

**Чому P-256, а не Ed25519/X25519.** Обидві платформи підтримують P-256
вбудованими засобами. Ed25519 у Windows CNG доступний не скрізь, а тягнути
libsodium заради нього суперечило б вимозі мінімуму залежностей.

Сумісність реалізацій перевірена: HKDF усіх трьох сторін збігається
з контрольним вектором RFC 5869, а підпис, створений на Windows, успішно
перевіряється в Node.

### Ключ наскрізного шифрування

```text
shared    = ECDH(власний_приватний, чужий_публічний)
session_k = HKDF-SHA256(shared,
                        salt = ідентифікатори обох пристроїв у сталому порядку,
                        info = "claude-monitor-v1/e2ee")
```

Сталий порядок ідентифікаторів гарантує, що обидві сторони отримають
однаковий ключ незалежно від того, хто рахує.

### Nonce

```text
12 байтів = [4 байти напрямку] ‖ [8 байтів лічильника]
```

Напрямок (`B2M ` або `M2B `) не дає збігтися nonce у зустрічних потоках.
Лічильник монотонний і **ніколи не йде на друге коло**: при досягненні межі
шифрування зупиняється, бо повторний nonce у GCM розкриває відкритий текст.

## 4. Підключення телефона

Ключова властивість: **Relay бере участь у передачі, але не може підмінити
ключі**, бо не знає коду.

```text
Bridge                        Relay                        Телефон
  │                             │                             │
  показує код                   │                             │
  │─── пропозиція + HMAC ──────>│  зберігає, коду не бачить    │
  │                             │<─── заявка + HMAC ───────────│ користувач
  │<─── заявка (переслано) ─────│                             ввів код
  │                             │                             │
  ПЕРЕВІРЯЄ HMAC кодом          │                             │
  │─── згода ──────────────────>│──── згода + ключі ─────────>│
```

```text
confirm = HMAC-SHA256(HKDF(код), роль ‖ публічні ключі)
```

Роль входить у повідомлення, тож підтвердження однієї сторони не можна
повторити як підтвердження іншої.

| Параметр | Значення | Чому саме так |
|---|---|---|
| Ентропія коду | 60 бітів | підбір за 3 хвилини недосяжний |
| Час життя | 180 с | достатньо, щоб переписати код з екрана |
| Спроби | 5, далі 15 хв блокування | унеможливлює перебір |
| Одноразовість | так | код згорає після успіху |
| Зберігання коду | лише в памʼяті | на диск не потрапляє ніколи |

**Що дає можливість атаки.** Relay бачить HMAC і теоретично може підбирати
код офлайн. 2⁶⁰ операцій — це роки обчислень, а підміна ключів вимагала б
підбору **за 180 секунд**, доки пропозиція жива. Після pairing код узагалі
втрачає значення: довіра тримається на обмінених ключах.

## 5. Маскування секретів

> Це **додатковий** шар, а не основний захист (Частина 5 §23 Master Prompt).

Основний захист у тому, що Bridge узагалі не передає вміст файлів, повний
вивід команд і аргументи інструментів — лише короткі описи дій.

Master Prompt (Частина 3 §18) прямо застерігає від «універсального
regex-фільтра, який ламає звичайний вивід». Тому кожне правило вимагає
**явного контексту**:

| Правило | Приклад спрацювання | Що НЕ чіпає |
|---|---|---|
| присвоєння секретній змінній | `PASSWORD=hunter2` | слово `password` у тексті |
| відомий префікс токена | `sk-ant-…`, `ghp_…`, `AKIA…` | `sk-1`, короткі рядки |
| блок приватного ключа | `-----BEGIN … PRIVATE KEY-----` | публічний ключ |
| заголовок авторизації | `Authorization: Bearer …` | інші заголовки |
| облікові дані в URL | `https://user:pass@host` | звичайні адреси |

Правила «32 шістнадцяткові символи — це секрет» **немає навмисно**: воно
маскувало б хеші комітів і контрольні суми, роблячи вивід нечитабельним.

Шляхи на кшталт `.env`, `id_rsa`, `*.pem` не показуються навіть як назви:
сама наявність такого файлу буває чутливою.

Перевірено 16 тестами, з них 6 — саме на **відсутність** хибних спрацювань.

## 6. Захист Relay

| Механізм | Значення за замовчуванням |
|---|---|
| Розмір кадру | 64 КБ, більше — розрив без розбору |
| Нові зʼєднання з адреси | 30 сплеск, 2/с |
| Спроби автентифікації | 5, далі блокування на 60 с |
| Спроби pairing | 5, далі 15 хв |
| Частота кадрів | 120 сплеск, 40/с |
| Одночасних зʼєднань | 64 |
| Рукостискання | 15 с, далі розрив |

Ліміти винесені в конфігурацію: за одним NAT кілька пристроїв мають спільну
зовнішню адресу, і жорстко зашите значення блокувало б легітимних
користувачів.

Relay зберігає **лише** реєстр пристроїв: ролі, публічні ключі, звʼязки,
стан відкликання. Подій він не зберігає взагалі — маршрутизація ефемерна.

## 7. Захищені налаштування за замовчуванням

Частина 3 §23 Master Prompt вимагає, щоб небезпечний варіант не був
досяжним випадково.

| | |
|---|---|
| `ws://` замість `wss://` | відхиляється, якщо не передано явний прапорець |
| Режим `plain` на Relay | дозволений лише на локальному інтерфейсі, перевіряється в конфігурації |
| Перевірка сертифіката | увімкнена скрізь, вимкнути неможливо |
| Автоматичний відкат на незашифроване | **відсутній як явище** |
| Налагоджувальні записи в релізі | вирізаються R8 на етапі збірки |
| Секрети в репозиторії | немає; `.gitignore` покриває ключі й сховища |

## 9. Чесність тверджень

Частина 6 §42 Master Prompt забороняє перебільшувати. Тому:

**Правда:** події зашифровані наскрізно — Relay справді не може їх прочитати.
Ключі на телефоні зберігаються в Keystore. Застосунок справді не може
керувати ноутбуком.

**Не стверджується:** що система захистить від зловмисника, який уже
має контроль над ноутбуком. Що маскування секретів спіймає геть усе.
Що метадані трафіку приховані від оператора Relay.
