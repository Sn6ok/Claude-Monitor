# Протокол Claude Monitor v1

> Версія протоколу: **1**
> Кодування: UTF-8 JSON у текстових кадрах WebSocket
> Транспорт: WebSocket over TLS (WSS)

---

## 1. Два рівні протоколу

Протокол свідомо розділений на два незалежні рівні. Це прямий наслідок моделі
довіри з [architecture.md §8](architecture.md): Relay маршрутизує, але не читає.

```text
┌─────────────────────────────────────────────────────────┐
│  РІВЕНЬ 2: ПРИКЛАДНИЙ  (Bridge <-> Android)             │
│  SNAPSHOT, EVENT, SNAPSHOT_REQUEST, ACK                 │
│  ЗАШИФРОВАНО наскрізно — Relay не бачить вміст          │
├─────────────────────────────────────────────────────────┤
│  РІВЕНЬ 1: ТРАНСПОРТНИЙ  (пристрій <-> Relay)           │
│  HELLO, CHALLENGE, AUTH, AUTH_OK, FORWARD, PAIR_*, ERROR│
│  Relay читає та валідує — це його робота                │
├─────────────────────────────────────────────────────────┤
│  WebSocket over TLS 1.2+                                 │
└─────────────────────────────────────────────────────────┘
```

## 2. Загальна форма кадру рівня 1

```json
{
  "v": 1,
  "t": "auth",
  "id": "01HQ8...",
  "ts": 1770000000123,
  "p": { }
}
```

| Поле | Тип | Обов'язкове | Обмеження | Призначення |
|---|---|---|---|---|
| `v` | integer | так | рівно `1` | версія протоколу |
| `t` | string | так | 1–24 символи, `[a-z_.]` | тип кадру |
| `id` | string | так | 26 символів, ULID | ідентифікатор кадру для `ack` |
| `ts` | integer | так | Unix ms, вікно ±300 с | час відправника |
| `p` | object | залежить від `t` | див. нижче | корисне навантаження |

### Жорсткі ліміти (Частина 3 §19, Частина 4 §21)

| Константа | Значення | Що обмежує |
|---|---|---|
| `MAX_FRAME_BYTES` | 65 536 | розмір одного кадру WebSocket |
| `MAX_EVENT_TEXT` | 3072 | текст в одній події; довше — частинами (§6.2) |
| `MAX_OUTPUT_BYTES` | 262 144 | один запис — репліка, запит, команда чи її вивід — сумарно всіма частинами; межа лише запобіжна |
| `MAX_EVENTS_PER_BATCH` | 8 | подій в одному пакеті |
| `MAX_SESSIONS` | 16 | одночасно відстежуваних задач |
| `MAX_QUEUE_EVENTS` | 512 | глибина черги Bridge |
| `MAX_SNAPSHOT_EVENTS` | 20 | подій на задачу в snapshot |
| `MAX_SNAPSHOT_TEXT` | 3072 | текст події в snapshot — повністю; щоб знімок вмістився в кадр, зменшується кількість подій, а не текст |
| `CLOCK_SKEW_SEC` | 300 | допустимий розбіг годинників |

Кадр, що порушує будь-який ліміт, **відхиляється до розбору вмісту**.
Перевищення `MAX_FRAME_BYTES` розриває з'єднання без спроби парсингу —
це захист від вичерпання пам'яті (Частина 4 §21).

## 3. Рівень 1 — типи кадрів

### 3.1 `hello` — представлення (клієнт -> Relay)

```json
{ "v":1, "t":"hello", "id":"...", "ts":..., "p":{
    "role": "bridge",
    "device_id": "b3f1...64hex",
    "client": "claude-monitor-bridge/1.0.0"
}}
```

`role`: `"bridge"` або `"monitor"`. `device_id` — SHA-256 від публічного
ключа підпису пристрою, у нижньому регістрі hex.

### 3.2 `challenge` — виклик (Relay -> клієнт)

```json
{ "v":1, "t":"challenge", "id":"...", "ts":..., "p":{
    "nonce": "<32 байти, base64url>",
    "expires_at": 1770000030000
}}
```

Nonce створюється криптографічним ГВЧ сервера, дійсний 30 секунд,
використовується **рівно один раз** (Частина 3 §10).

### 3.3 `auth` — відповідь на виклик (клієнт -> Relay)

```json
{ "v":1, "t":"auth", "id":"...", "ts":..., "p":{
    "device_id": "b3f1...",
    "sig": "<ECDSA P-256 підпис, base64url>"
}}
```

Підписується рядок:

```text
"claude-monitor-v1|auth|" + role + "|" + device_id + "|" + base64url(nonce)
```

Префікс із назвою протоколу — domain separation, щоб підпис із одного
контексту не можна було використати в іншому.

### 3.4 `auth_ok` (Relay -> клієнт)

```json
{ "v":1, "t":"auth_ok", "id":"...", "ts":..., "p":{
    "session_token": "<opaque, base64url>",
    "peer_online": true,
    "peers_online": ["<device_id телефона>", "..."],
    "server_time": 1770000000500
}}
```

`peer_online` дозволяє Android одразу показати «ноутбук офлайн»,
не чекаючи таймауту. `peers_online` отримує лише Bridge: до нього можна
підключити до п'яти телефонів, і кожному, що в мережі, потрібен власний знімок.

### 3.5 `fwd` — маршрутизація (двонаправлений)

Це єдиний кадр, що переносить прикладні дані. Relay **не може** прочитати `ct`.

```json
{ "v":1, "t":"fwd", "id":"...", "ts":..., "p":{
    "n":  "<12 байт nonce AES-GCM, base64url>",
    "ct": "<шифротекст + 16-байтний тег, base64url>",
    "to": "<device_id адресата, необов'язково>"
}}
```

Bridge шифрує кожному телефону його власним ключем і тому вказує адресата
в `to`: кадр доходить лише до нього. Без `to` кадр іде всім партнерам
відправника. Relay додає до пересланого кадру `from` — `device_id`
відправника; за ним Bridge обирає ключ, яким розшифрувати кадр від телефона.

Що бачить Relay: факт передачі, розмір, час, `device_id` відправника
й отримувача. Що не бачить: **нічого зі вмісту** — ані `session_id`,
ані шляхів до файлів, ані тексту.

### 3.6 `ping` / `pong`

Порожній `p`. Інтервал — **45 секунд** без активності.

Обґрунтування інтервалу (Частина 5 §21): типовий NAT-таймаут мобільних
операторів становить 60–120 с; Cloudflare розриває неактивний WebSocket
через 100 с. 45 с дає запас і при цьому дає лише ~1900 кадрів на добу
(~110 КБ) — знехтувано мало для батареї й трафіку.

### 3.7 `error`

```json
{ "v":1, "t":"error", "id":"...", "ts":..., "p":{
    "code": "auth_failed",
    "retry_after": 30
}}
```

| Код | Значення | Дія клієнта |
|---|---|---|
| `bad_frame` | не пройшов валідацію | розірвати, backoff |
| `proto_unsupported` | інша версія протоколу | **показати «оновіть застосунок»**, не перепідключатися |
| `auth_failed` | підпис не збігся | не повторювати автоматично |
| `device_revoked` | пристрій відкликано | стерти локальні ключі, показати екран pairing |
| `rate_limited` | ліміт вичерпано | чекати `retry_after` |
| `peer_online` | партнер з'явився в мережі; `device_id` — котрий саме | Bridge надсилає цьому телефону знімок |
| `peer_offline` | інша сторона не в мережі; `device_id` — котрий саме (якщо відомо) | залишатись підключеним, показати статус |
| `too_large` | перевищено ліміт розміру | розірвати |

Повідомлення про помилку **ніколи** не містить деталей винятків,
стек-трейсів чи внутрішніх шляхів (Частина 4 §22).

## 4. Pairing

### 4.1 Модель загроз саме для pairing

Relay пересилає повідомлення pairing, але **не повинен мати змоги
підмінити ключі** (атака «людина посередині» з боку самого сервера).
Тому володіння кодом підтверджується HMAC, а код Relay ніколи не бачить.

### 4.2 Формат коду

```text
KXQ7-M4NP-2WRF
```

12 символів Base32 (алфавіт RFC 4648 без `I`, `L`, `O`, `U` — щоб не плутати
з цифрами), три групи по чотири. **60 біт ентропії.**

| Параметр | Значення |
|---|---|
| Час життя | 180 секунд |
| Кількість спроб | 5, далі блокування на 15 хвилин |
| Одноразовість | код анулюється після першого успішного pairing |
| Зберігання | лише в пам'яті Bridge, ніколи не на диску |

### 4.3 Похідні ключі

```text
PK = HKDF-SHA256(ikm = code_bytes,
                 salt = "claude-monitor-v1/pairing",
                 info = "",
                 L = 32)
```

### 4.4 Послідовність

```text
НОУТБУК (Bridge)                 RELAY                    ТЕЛЕФОН (Monitor)
      │                            │                            │
  генерує код,                     │                            │
  показує користувачу              │                            │
      │                            │                            │
      │──── pair_offer ───────────>│                            │
      │  {offer_id, bridge_pub_sig,│                            │
      │   bridge_pub_ecdh,         │  зберігає на 180 с,        │
      │   confirm_b}               │  НЕ знає коду              │
      │                            │                            │
      │                            │   користувач вводить код   │
      │                            │<──── pair_claim ───────────│
      │                            │  {offer_id, phone_pub_sig, │
      │                            │   phone_pub_ecdh, confirm_p│
      │<─── pair_claim (переслано)─│                            │
      │                            │                            │
  ПЕРЕВІРЯЄ confirm_p              │                            │
  локально, кодом                  │                            │
      │                            │                            │
      │──── pair_ok ──────────────>│──── pair_ok ──────────────>│
      │                            │                    ПЕРЕВІРЯЄ confirm_b
      │                            │                            │
  обидві сторони: ECDH -> HKDF -> спільний ключ E2EE            │
```

Коди підтвердження:

```text
confirm_b = HMAC-SHA256(PK, "bridge"  || bridge_pub_sig || bridge_pub_ecdh)
confirm_p = HMAC-SHA256(PK, "monitor" || phone_pub_sig  || phone_pub_ecdh)
```

Оскільки Relay не знає коду, він не може підробити жодне з підтверджень.
Підміна ключів вимагала б підбору 60-бітного секрету **за 180 секунд** —
недосяжно.

Після pairing код більше не потрібен: довготривала довіра тримається
на обмінених публічних ключах (Частина 3 §7).

## 5. Криптографія

| Призначення | Алгоритм | Windows | Android |
|---|---|---|---|
| Ідентичність / підпис | **ECDSA P-256 + SHA-256** | CNG `BCRYPT_ECDSA_P256` | Keystore `EC secp256r1` |
| Узгодження ключа | **ECDH P-256** | CNG `BCRYPT_ECDH_P256` | Keystore `ECDH` |
| Похідні ключі | **HKDF-SHA256** | CNG `BCRYPT_KDF_HKDF` | `javax.crypto.Mac` |
| Шифрування вмісту | **AES-256-GCM** | CNG `BCRYPT_AES` GCM | `AES/GCM/NoPadding` |
| Зберігання ключа | **DPAPI** (`CRYPTPROTECT_UI_FORBIDDEN`) | — | Android Keystore, апаратний за наявності |

P-256 обрано замість Ed25519/X25519 свідомо: обидві платформи підтримують
його **вбудованими засобами**, без жодної зовнішньої криптобібліотеки.
Ed25519 у Windows CNG доступний не на всіх підтримуваних збірках, а тягнути
libsodium заради цього суперечило б вимозі мінімальних залежностей
(Частина 3 §25, Частина 6 §39).

### Ключ сесії E2EE

```text
shared    = ECDH(власний_приватний_ecdh, чужий_публічний_ecdh)
session_k = HKDF-SHA256(ikm = shared,
                        salt = sorted(device_id_bridge, device_id_phone),
                        info = "claude-monitor-v1/e2ee",
                        L = 32)
```

### Nonce для AES-GCM

```text
12 байт = [4 байти напрямку] || [8 байт лічильника]
```

Напрямок: `"B2M "` або `"M2B "`. Лічильник монотонний, **ніколи не повторюється**
в межах пари ключів. Досягнення межі лічильника змушує повторне узгодження ключа.
Це прибирає ризик повторного використання nonce — найнебезпечнішої помилки в GCM.

Ключ сесії між з'єднаннями не змінюється, тож лічильник нового з'єднання
**не може починатися з нуля**: саме так було до виправлення, і після кожного
перепідключення nonce повторювались. Тепер старт такий:

- Bridge — секунди Unix, зсунуті на 16 біт (до 65 536 повідомлень на кожну
  секунду часу), і не нижче за будь-який номер, уже виданий цим процесом;
- Android — мілісекунди Unix, помножені на 1024: телефон надсилає лише
  кілька запитів за з'єднання, тож діапазони сусідніх з'єднань не перетинаються.

Кожен телефон має власний ключ (сіль HKDF містить його `device_id`), тож
лічильники різних телефонів одне одному не заважають.

## 6. Рівень 2 — прикладні повідомлення

Усе нижче передається **всередині** `fwd.p.ct` у зашифрованому вигляді.

### 6.1 `snapshot` (Bridge -> Monitor)

Повний стан усіх відстежуваних задач. Надсилається при підключенні,
після reconnect і при виявленні розриву послідовності.

```json
{
  "t": "snapshot",
  "seq": 1042,
  "bridge": {
    "host": "DESKTOP-A1",
    "version": "1.0.0",
    "uptime_sec": 3820,
    "claude_desktop": "running",
    "cpu_pct": 0.1,
    "rss_mb": 4.2
  },
  "summary": {
    "active": 3, "working": 2, "waiting": 1,
    "idle": 0, "finished": 4, "error": 0
  },
  "sessions": [
    {
      "sid": "fa676105-0796-4700-a4ca-2014ea84e18e",
      "short": "fa676105",
      "title": "Master prompt виконання",
      "title_src": "custom",
      "project": "Claude Monito",
      "branch": "main",
      "state": "working",
      "activity": { "action": "edit_file", "target": "bridge/src/main.cpp" },
      "started_at": 1788953990322,
      "last_update": 1788957810500,
      "seq": 1042,
      "turn_started_at": 1788957790000,
      "last_turn_ms": 192500,
      "events": [ ]
    }
  ]
}
```

Поле `title_src` — чесне джерело назви, щоб UI не видавав здогадку за факт:

| `title_src` | Звідки | Надійність |
|---|---|---|
| `custom` | `custom-title.customTitle` | назва задана явно |
| `derived` | `sessions/<pid>.json` -> `name` | автоматична назва Claude Code |
| `prompt` | `last-prompt.lastPrompt`, обрізано до 60 символів | з тексту запиту |
| `path` | остання частина `cwd` | лише каталог, назви немає |

### 6.2 `events` (Bridge -> Monitor)

Пакет подій. Кожна подія **обов'язково** належить конкретній задачі.

```json
{
  "t": "events",
  "items": [
    { "sid":"fa676105-...", "seq":1043, "ts":1788957811000,
      "k":"activity", "action":"run_command", "target":"npm test" },

    { "sid":"fa676105-...", "seq":1044, "ts":1788957814200,
      "k":"result", "status":"success", "text":"42 tests passed" },

    { "sid":"9c02aa71-...", "seq":1045, "ts":1788957815000,
      "k":"status", "state":"waiting", "text":"Дозволити запис у файл?" }
  ]
}
```

Поле `sid` є в **кожній** події без винятку. Це технічна гарантія вимоги
«події однієї задачі не повинні з'являтися під іншою»: подія без `sid`
або з невідомим `sid` **відкидається** приймачем, а не приписується
активній задачі.

#### Види подій `k`

| `k` | Поля | Приклад |
|---|---|---|
| `status` | `state`, `text?`, `turn_start?`, `turn_ms?` | зміна стану задачі; час відповіді — нижче. Для `limited` у `text` — час скидання ліміту |
| `activity` | `action`, `target?` | `edit_file` / `bridge/src/main.cpp` |
| `output` | `text` | текстова репліка Claude |
| `prompt` | `text?`, `img?` | повідомлення користувача; `img` — скільки зображень було надіслано (самі зображення не передаються) |
| `result` | `status`, `text` | `success` / `42 tests passed` |
| `session` | `event` | `started`, `ended` |

#### Довгі репліки: частини

Текст понад `MAX_EVENT_TEXT` — репліка, запит, вивід команди, а в `activity` і сама ціль (`target`) — передається кількома подіями поспіль. Кожна
частина несе три додаткові поля:

| Поле | Значення |
|---|---|
| `gid` | спільний номер усіх частин однієї репліки |
| `pt` | номер частини, від 0 |
| `pc` | скільки частин усього |

Розрив робиться по межі рядка, потім по пробілу і лише в останню чергу —
по межі символу UTF-8. Приймач склеює частини з однаковими `sid` і `gid`
в одне повідомлення; пропущену частину позначає `…`, а не приховує.
Звичайна подія цих полів не має.

Приймач **накопичує** події, а не замінює їх знімком: `snapshot` лише
доповнює історію тим, чого в ній ще немає. Упізнавання йде за відбитком
(`sid`, `ts`, `k`, початок тексту), а не за `seq` — після перезапуску
Bridge номери послідовності починаються заново.

#### Час відповіді

Відповідь — це хід від запиту користувача до завершення відповіді Claude
(`end_turn`) або до переривання. Помилка інструмента й очікування дозволу
відповідь не переривають.

| Поле | Де | Значення |
|---|---|---|
| `turn_start` | `status` зі станом `working`, `error`, `waiting` | коли почалась поточна відповідь, мс Unix |
| `turn_ms` | `status` зі станом `idle` або `limited` | скільки тривала відповідь, мс |
| `turn_started_at` | сесія в `snapshot` | те саме, що `turn_start`, для початкового стану |
| `last_turn_ms` | сесія в `snapshot` | тривалість останньої завершеної відповіді |

Поля передаються **лише коли значення відоме**. Якщо Bridge запустився
посеред відповіді й її початку не бачив, ні початку, ні тривалості
він не надсилає — вигаданий час гірший за відсутній (Частина 5 §12).
Тиша в транскрипті стану не змінює: поки Claude довго думає, записів
немає, і це не простій. Стан змінюють лише докази — рядки транскрипту,
хуки та завершення процесу.

#### Значення `action`

```text
read_file  edit_file   write_file   run_command  search
web_fetch  task        subagent     other
```

Невідомий інструмент дає `other` — не вигадану назву (Частина 5 §12).

### 6.3 `snapshot_request` (Monitor -> Bridge)

```json
{ "t": "snapshot_request", "since_seq": 1042 }
```

Надсилається після автентифікації, після reconnect і при виявленні
пропуску в нумерації.

### 6.4 `ack` (Monitor -> Bridge)

```json
{ "t": "ack", "seq": 1045 }
```

Дозволяє Bridge звільнити чергу. Відсутність `ack` **ніколи не блокує**
Bridge — черга просто витісняє старі події за пріоритетом.

---

## 7. Нумерація й виявлення втрат

`seq` — монотонний лічильник **на весь Bridge** (не на задачу).
Це дає єдиний глобальний порядок для стрічки подій усіх задач одразу.

```text
отримано 1042, 1043, 1044, 1047
                          ↑
                 пропуск 1045-1046
                          │
                          ▼
              snapshot_request(since_seq=1044)
                          │
                          ▼
                 повний snapshot -> стан відновлено
```

Порядок визначається **тільки** через `seq`, ніколи через `ts`
(Частина 4 §24–25). `ts` існує лише для показу користувачу.

---

## 8. Пріоритети подій

При переповненні черги (мережа відсутня) витіснення йде знизу вгору.

| Пріоритет | Події | Витісняється |
|---|---|---|
| **HIGH** | `status`, `session`, `result` зі `status:"error"` | ніколи |
| **MEDIUM** | `result` успішний, `activity`, `output`, `prompt` | після LOW |
| **LOW** | повторювані `activity` того самого типу | першим |

Гарантія: **зміна стану задачі не губиться ніколи**. Користувач може
не побачити частину проміжного виводу, але завжди побачить, що задача
завершилась або впала з помилкою.

---

## 9. Узгодження версій

```text
Клієнт надсилає v=1
         │
         ├── Relay підтримує 1 -> працюємо
         │
         └── Relay не підтримує -> error{proto_unsupported}
                                   з'єднання закривається,
                                   клієнт НЕ перепідключається,
                                   UI: «Оновіть застосунок»
```

Невідомі **поля** всередині відомого типу кадру ігноруються — це дає
сумісність уперед. Невідомий **тип** кадру відхиляється (Частина 4 §23).

---

## 10. Політика reconnect

Однакова для Bridge і Android (Частина 2 §13, Частина 4 §10):

```text
спроба:  1     2     3     4     5     6     7+
пауза:   1с    2с    4с    8с    16с   30с   60с (стеля)
джитер:  ±20% від паузи
```

Джитер обов'язковий: без нього після падіння Relay всі клієнти
повернуться синхронно і створять сплеск навантаження.

Лічильник скидається після **успішної автентифікації**, а не після
встановлення TCP-з'єднання — інакше цикл «підключився, впав на авторизації»
перетворився б на агресивний цикл (Частина 5 §20).

### Після відновлення зв'язку

```text
TLS -> hello -> challenge -> auth -> auth_ok -> snapshot_request -> snapshot
```

Повний snapshot надсилається завжди. Bridge **не намагається** відтворити
пропущені події з історії — це прибирає потребу зберігати довгу історію
будь-де (Частина 2 §14).

---

## 11. Правила валідації

Кожен кадр проходить перевірки **в цьому порядку**, з виходом на першій невдачі:

```text
1. розмір <= MAX_FRAME_BYTES        (інакше розрив без парсингу)
2. коректний UTF-8 JSON
3. v == 1
4. t належить відомій множині
5. id — рівно 26 символів ULID
6. |ts - зараз| <= CLOCK_SKEW_SEC
7. форма p відповідає типу t
8. довжина кожного рядкового поля в межах ліміту
9. стан з'єднання дозволяє цей тип кадру
10. для fwd: відправник автентифікований і авторизований на отримувача
```

Порядок не випадковий: спершу дешеві перевірки, потім дорогі.
Кадр 10 МБ відхиляється на кроці 1, не досягнувши парсера JSON.

---

## 12. Що протокол дозволяє додати пізніше

Частина 2 §11 вимагає закласти можливість зворотного напрямку,
але **не реалізовувати** його зараз.

Зарезервовані типи рівня 2 — Relay їх пересилає, але поточні
Bridge і Android відхиляють як невідомі:

```text
command.stop      command.pause      command.resume
```

Реалізація потребуватиме окремого дозволу на рівні Relay
(`role: monitor` наразі має право лише читати) і явного підтвердження
користувача. У версії 1 Android **строго read-only** (Частина 4 §27).
